| G15 | 🐞 **SECURITY — any caller of `GetKeywordTree` (exposed with zero auth as `mwanachama-backend-api-kazi`'s `git_get_keyword_tree` MCP tool) can force an unbounded, arbitrarily expensive response by naming a keyword with a large subtree, unlike every sibling List method in this repo.** `git_impl_keywords.go`'s `GetKeywordTree`/`buildKeywordTreeNode` walk every descendant via `gormstore.KeywordChildIDs`, which runs a plain `Pluck("id", &ids)` with **no `.Limit()` and no depth cap at all** — recursing one full DB query per level, at every fan-out, with no backstop. This is the one exception to `list_limit.go`'s own stated invariant ("`maxListPage` caps every List* method reachable through the /mcp surface"): `ListKeywords` itself is correctly capped (`limit <= 0 || limit > maxListPage → limit = maxListPage`), and `KeywordDescendantIDs`'s own recursive CTE documents an explicit `depth<32` backstop for the same reachability shape — `GetKeywordTree` alone has neither. Demonstrated live (throwaway probe, not committed): seeded one root keyword with 600 direct children (`maxListPage` is 500) via a real `*gitManager` over sqlite, then called `GetKeywordTree(ctx, rootID)` directly — returned all 600 child nodes uncapped, confirming the absence of any cap at the point this scheduled sweep found it. Currently reachable by literally anyone: `mwanachama-backend-api-kazi` mounts `/mcp` with no transport-level auth wrapper and `RequireCapability` is a stub that allows every call (K7/K8, already tracked separately — not the defect this row is about; this bug hits an authenticated caller too, once K7/K8 lands, since neither List cap nor depth guard exists at any layer). **Fix location**: `gormstore/queries.go`'s `KeywordChildIDs` needs the same `maxListPage` cap `ListKeywords`/every other List method already has, and `buildKeywordTreeNode`'s recursion needs a depth backstop mirroring `KeywordDescendantIDs`'s documented `depth<32`. Sibling finding filed the same run: `mwanachama-backend-taskmanager`'s W21 (`TraverseRelationships`, the identical loophole class — a graph-walk method that skipped the package's own list-capping convention). | 📋 | — |
| G13 | Index pushed tags as `Tag` rows. A `git push origin v1.0.0` stores the ref in the bare repo and clones back correctly, but produces no `Tag` row, so `ListTags` reports nothing for a repository that has tags. Both kinds need handling and they differ: a lightweight tag's ref points straight at a commit, an annotated tag's at a tag object carrying its own message/tagger. Guard already in place — `IndexPushedBranch` skips non-`refs/heads/` refs rather than filing them as bogus Branch rows (`TestRealGit_TagPushIsStoredInGitButNotIndexedAsABranch` pins both halves; update it with the fix) | 📋 | — |

| G14 | 🐞 **BUG — a real `git clone --depth N` (or `git fetch --depth N`) against `SmartHTTPHandler` fails outright with `fatal: Server does not support shallow clients` / `fatal: the remote end hung up unexpectedly` (exit 128), instead of serving a shallow clone or refusing with a caller-legible message.** Root cause is one layer down: go-git v5.16.5's own server-side upload-pack session (`plumbing/transport/server/server.go`) hard-refuses any request whose `Shallows` list is non-empty (`"shallow not supported"`), and `git_smarthttp.go`'s `uploadPack` handler passes every client request through to that session unmodified — there is no capability check or pre-validation that would let a real client negotiate a full clone instead, or fail cleanly before the protocol hangs up. Confirmed by test: pushed a real 3-commit history, a full (non-shallow) `git clone` of the same repo succeeds with all 3 commits, but `git clone --depth 1 <server>/<repo>` exits 128 and leaves no local repository at all — see `TestRealGit_ShallowCloneFailsOutright` (`git_realgit_shallow_test.go`, `integration`-tagged), which pins this exact failure. Defect location: `git_smarthttp.go`'s `uploadPack`, layered on the upstream go-git v5.16.5 limitation — the fix is either implementing real shallow support server-side or detecting a shallow request and refusing it with a clear message instead of the raw upstream error | 📋 | — |
