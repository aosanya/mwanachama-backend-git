| G17 | 🐞 **SECURITY — a single call to `GetKeywordTree` (`GET /keywords/tree?root=`, and `mwanachama-backend-api-kazi`'s `git_get_keyword_tree` MCP tool, which calls the same manager method directly) forces this service to walk and serialize an entire keyword taxonomy with no depth or node-count bound.** Found during a scheduled security sweep of `mwanachama-backend-api-kazi` (this method is one of its 14 read-only git tools) while checking the Cost/Availability shape ("an unbounded fan-out tool") — kazi's own `RequireCapability` is currently a no-op stub (K7/K8, already tracked there), so today ANY caller who can reach `/mcp` at all can trigger this, not just an authorized-but-careless one. Every sibling read in this same file is bounded: `ListKeywords` clamps to `maxListPage` (500, `git_impl_keywords.go` ~line 124), and the neighboring graph-traversal method `GetNeighborhood` clamps both depth (`clampDepth`, range [1,3]) and total node count (`neighborhoodMaxNodes` = 100, `git_impl_graph.go`). `GetKeywordTree`'s own recursive helper, `buildKeywordTreeNode` (`git_impl_keywords.go` ~line 224), has neither: it recurses one extra pair of DB queries per child, however many descendants the given root actually has, and `GetKeywordTree("")` walks "the full forest of root keywords" — every keyword in the store — in one call. Confirmed two ways: (1) directly against the manager over an in-memory sqlite store, a 2000-deep keyword chain returned all 2000 nodes with zero truncation; (2) through the real HTTP router (`routes.Routes` over a real `net/http/httptest` server), pinned as `routes/keyword_tree_unbounded_test.go`'s `TestG17_KeywordTreeHasNoDepthOrCountBound` — a 600-deep chain (past `maxListPage`) comes back whole, contrasted with the same router's `ListKeywords` route, which is capped. Threat: any MCP or HTTP caller reachable today, holding nothing but the ability to name (or omit) a keyword id, can force O(N) sequential, unbatched DB round trips and an unbounded-size JSON response for a taxonomy of any size the deployment has grown to — a resource-exhaustion path with no authorization bypass needed, the availability twin of the already-bounded reads beside it. Fix: give `GetKeywordTree` the same two bounds `GetNeighborhood` already has — a maximum depth and a maximum total node count, truncating or refusing past either — the smallest change that brings it in line with every other read in this file. `TestG17_KeywordTreeHasNoDepthOrCountBound`'s "the full unbounded chain came back" assertion must invert into "truncated at the bound" once that lands. | 📋 | |
| G16 | 🐞 **BUG — `GET /branches/{branchID}/neighborhood/{entityID}` leaks a Blob's full content across repositories from a guessed filename alone, with no prior knowledge of any real id.** Widens G15's finding to the third method in the same graph-query family (`git_impl_graph.go`, same file). `GetNeighborhood` confirms `branchID` exists (~line 44) but its non-id-entityID fallback, `resolveEntityID` (~line 123), resolves a file path by a bare `Where("path = ? AND NOT deleted", entityID)` against `m.tables.Blobs` — the **entire deployment's** Blob table, not just blobs reachable from that branch. Driven through the real aggregator (`routes.Routes`) over a real `http.ServeMux`/`http.Client`: repo A ("victim") gets `secrets.txt` = `REPO-A-SECRET-CONTENT`; repo B ("attacker", no relationship to A) gets its own unrelated file. The attacker calls `GET /branches/<their own branch>/neighborhood/secrets.txt?depth=1` — never having learned the victim's branch, repo, or blob id — and gets back, verbatim: `nodes:[map[... path:secrets.txt content:REPO-A-SECRET-CONTENT ...] ...]`. This is a strictly easier attack than G15's (which needs a discoverable keyword id for the `/search/keywords` variant): here a guessed common filename (`secrets.txt`, `.env`, `README.md`, `id_rsa`) is the entire attack surface. Fix: `resolveEntityID`'s path fallback must scope the Blob lookup to blobs reachable from the given branch — the same join `ReadFile`/`ListDirectory`/`Log` already use (per this repo's own CLAUDE.md, which confirms those three are correctly branch-scoped) — rather than querying `m.tables.Blobs` globally by path. Pinned by `routes/graph_neighborhood_crossrepo_test.go`'s `TestG16_NeighborhoodByPathLeaksBlobsAcrossRepositories` (asserts today's broken cross-repo-visible behavior; must invert once branch scoping lands). | 📋 | |
| G15 | 🐞 **BUG — `POST /graph/query` and `POST /search/keywords` leak every Blob's full content across repositories, to any caller who only owns their own unrelated branch.** Driven through the real aggregator (`routes.Routes`) over a real `http.ServeMux`/`http.Client`, not the manager directly. Setup: repo A ("victim") gets a file `secrets.txt` with content `REPO-A-SECRET-CONTENT`; repo B ("attacker", no relationship to repo A) gets its own unrelated file `mine.txt`. Observed: `POST /graph/query` with `{"branch_id": <attacker's own branch>}` returns **both** blobs, including `secrets.txt`/`REPO-A-SECRET-CONTENT` verbatim — full real HTTP response: `map[edges:[] nodes:[map[... path:mine.txt ...] map[... path:secrets.txt content:REPO-A-SECRET-CONTENT ...]]]`. Widened to the sibling handler in the same file: after tagging the victim's secret blob with a keyword, `POST /search/keywords` with `{"branch_id": <attacker's own branch>, "keywords": [<that keyword id>]}` returns the victim's `secrets.txt` too, despite the attacker never learning the victim's branch or blob id — only a keyword id, itself discoverable via the ungated `GET /keywords` list. Root cause (`git_impl_graph.go`): both `QueryGraph` (~line 454) and `SearchByKeywords` (~line 293) call `m.GetBranch(ctx, req.BranchID)` only to confirm the branch **exists** — the actual query (`m.tables.Blobs` for `QueryGraph`, `m.tables.BlobKeywordTags` for `SearchByKeywords`) is never filtered by that branch or its repository, contradicting both types' own doc comments (`models.go`'s `QueryGraphRequest.BranchID`: "the branch scope"; `SearchByKeywordsRequest.BranchID`: "Only entities reachable from this branch are considered"). This repo's own CLAUDE.md already names the gap as a known, pre-existing, not-yet-fixed limitation ("QueryGraph and SearchByKeywords still don't filter by req.BranchID... a real, pre-existing gap") but it had never been filed as a board row or demonstrated through the real HTTP surface before this sweep — with two separate repositories in play it is a genuine cross-tenant content leak, not just an internal-note curiosity. `GetNeighborhood` (the third method in the same graph-query family, same file) was not probed this run — worth checking next, though it needs a caller to already know a real entity id rather than discovering one from nothing. Fix: filter both queries to blobs reachable from `req.BranchID`'s own repository (e.g. join through `git_tree_blobs`/commit history the way `ReadFile`/`Log` already scope by branch) before applying the existing signal/keyword/file-type filters. Pinned by `routes/graph_crossrepo_test.go`'s `TestG15_QueryGraphLeaksBlobsAcrossRepositories` and `TestG15_SearchByKeywordsLeaksBlobsAcrossRepositories` (both assert today's broken cross-repo-visible behavior; must invert once branch scoping lands). | 📋 | |
