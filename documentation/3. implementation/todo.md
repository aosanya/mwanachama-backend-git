| G15 | 🐞 **SECURITY — `GetKeywordTree` (`git_impl_keywords.go`) has no result cap, unlike every sibling `List*` method in this file, and is reachable with zero authentication via `mwanachama-backend-api-kazi`'s `git_get_keyword_tree` MCP tool.** Filed by the 2026-09-19 scheduled security-QA sweep (primary repo: `mwanachama-backend-api-kazi`; root cause traced here since `GetKeywordTree` is `GitManager`'s own method). **Did:** called `GetKeywordTree(ctx, "")` directly against a real `*gitManager` (sqlite-backed, mirroring `testdb_test.go`'s harness) after seeding 2000 root `Keyword` rows — a wide-but-shallow taxonomy, plausible in production for a service that tags/documents across every indexed repository. **Observed:** all 2000 nodes returned in one call, `buildKeywordTreeNode` recursing once per node with no depth cap and no node-count cap (confirmed by reading the recursion in `git_impl_keywords.go`'s `GetKeywordTree`/`buildKeywordTreeNode`: each level issues two more DB queries — `gormstore.KeywordChildIDs` then a `Find` — with no `LIMIT` anywhere in the call chain). Reproduced with a throwaway test (`TestSecurityProbeKeywordTreeUnbounded`, written then deleted per this sweep's own rule against permanently filing an unfixed case as a green self-test). **Threat:** every sibling read this file exposes (`ListKeywords`, and every other domain's `ListRepositories`/`ListBranches`/`ListTags`/`ListMergeRequests`) caps at `maxListPage=500` (`list_limit.go`) — this method alone skips that convention, and its own MCP wrapper (`mcp_tools_git.go`'s `git_get_keyword_tree` in `mwanachama-backend-api-shared`) exposes it with a single optional `keyword_id` param and no `Limit`/depth field at all. On `mwanachama-backend-api-kazi` specifically, `/mcp` currently requires no credential at all and `RequireCapability` is a hard allow-all stub (K7/K8, an already-tracked, separate gap — not re-filed here), so this recursive, uncapped query cascade is reachable today by literally any caller who can open a TCP connection to the service, with a single tool call carrying no arguments. A taxonomy of realistic production size (tens of thousands of keywords, easily reached by an active documentation/tagging habit across many repos) turns one such call into tens of thousands of sequential DB round trips — a cheap, repeatable way to exhaust the DB connection pool / CPU for the whole service, not scoped to the caller's own data. **Control:** none — no `Limit`/`MaxDepth` field exists anywhere in `GetKeywordTree`'s signature, `KeywordTreeNode`, or the MCP tool's params struct. **Verdict:** OPEN.
